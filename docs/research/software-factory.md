# Из чего собирать Software Factory в Agent Kit

Исследование для обсуждения, 21 ноября 2026 года. Вопрос: где описать маршрут от задачи до поставки, чтобы проект мог менять правила и подключать практики, а отдельные скиллы сохраняли самостоятельную ценность?

**Предложение для Kit.** Описать переходы между этапами в одном проектном workflow. Практику держать у её исполнителя, право на действие — в правилах проекта, результат конкретного запуска — в задаче или PR. Пока работой управляет интерактивная сессия, ведущий агент способен пройти такой маршрут по инструкции. В определении Мэтта фабрика начинается с первого события, которое само запускает агентную сессию. Например, владелец ставит метку на готовую задачу, GitHub Actions запускает реализацию, результатом становится PR. Тот же исполнитель событий может позже возобновлять работу после решения человека. [Определение Мэтта](https://www.aihero.dev/ai-coding-dictionary/software-factory)

## Что обнаружилось у Мэтта Покока

У Мэтта есть два масштаба координации. Внутри одной спецификации `implement-spec` разбирает зависимости тикетов, передаёт исполнителям ссылки вместо копий контекста, объединяет изменения и вызывает ревью. В этой задаче порядок действий — часть самой практики. Выносить каждый внутренний вызов в общую схему пришлось бы даже для того, чтобы поменять способ работы одного скилла. [Статья Мэтта о выпуске v1.3](https://www.aihero.dev/skills-changelog-v13-implement-spec-pr-retro-and-glossary-md) · [Исходник implement-spec](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/engineering/implement-spec/SKILL.md)

Для работы между сессиями у него другая модель. Тип задачи определяет полезную работу, событие инициирует конкретный запуск, оркестратор учитывает очередь и исполнение. Git и трекер сохраняют состояние после окончания запуска. Если нужен человек, запуск заканчивается, а последующее действие человека может начать следующий. При проектировании каждой задачи Мэтт предлагает определить её вход, результат, следующее событие, участие человека и защиту от двойного исполнения. GitHub Actions у него один из возможных оркестраторов. PR с этим описанием принят 31 октября. На проверенной ревизии исходник лежит в `skills/in-progress` и служит руководством для проектирования. [Software Factory на закреплённой ревизии](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/in-progress/software-factory/SKILL.md) · [История PR](https://github.com/mattpocock/skills/pull/1316)

В посте от 22 октября Мэтт показывает сами скиллы в работе: `/grill-me on how a /software-factory might help us`. Один скилл ведёт интервью, другой даёт термины и вопросы для выбора задач и инфраструктуры. По ссылке из поста PR добавляет инструкцию и справочные файлы. Среди примеров есть переход от реализации к ревью и ограниченный повтор ревью после исправления. Для Kit переносим описание перехода и его результата. Число запусков остаётся решением Kit: один вызов ревью на поставку. Метка на PR запускает другой workflow для ревью. В отдельном TypeScript-примере runner получает идентификатор задачи и ветку, создаёт рабочую копию и передаёт агенту файл инструкций. Срез исследования — `34cf38e2392e7dfbdc37807ff774db4a75cf0275`. Установщик уже различает наличие скилла, обязательную зависимость и опциональную практику. Эта информация отвечает на вопрос «что доставить в проект». Во время работы агенту нужен ответ на другой вопрос: «какой этап сейчас активен и по какому результату можно идти дальше?». Показательный случай — правило одного ревью. `implement` владеет разделом подготовки поставки. `implement-spec` ссылается на него, но также заново описывает исправления, тесты и Verify. `ship` повторяет условия завершённости Verify и объясняет восстановление после сбоя CI. Общее описание контракта и проектная Mermaid-схема также показывают этот порядок. Эти документы решают разные задачи, но при изменении границы между этапами редактору приходится определять, где правило первично. ## Предлагаемый расклад

| Если меняется… | Где менять | Кто использует |
| --- | --- | --- |
| Порядок этапов поставки и результат, разрешающий переход | Один короткий проектный `WORKFLOW.md`. Схема показывает его развилки. В начале достаточно текста и Mermaid рядом. | Ведущий агент, а при автоматизации — исполнитель событий |
| Метод практики | Скилл. Например, `code-review` отвечает за параллельные Standards и Spec, `implement-spec` — за граф тикетов. Внутреннюю координацию этих работ можно сохранить. | Вызвавший скилл получает результат |
| Выбор практик, владелец приёмки, право на слияние | Существующие правила проекта. Для пустого проекта — раздел настроек из setup. Workflow указывает, где читать эти решения. | Ведущий агент, классификатор и `ship` |
| Уровни тестирования, команды и среда | Проектный `testing.md`. Требования отдельной фичи записываются в задаче или спецификации. | Проектирование, TDD, Verify |
| Формат отчёта | Шаблон PR. Доказательства, статус, решение человека и версия результата принадлежат конкретному PR или записи локальной сдачи. | `pr` оформляет, `ship` обновляет статус и выполняет разрешённое действие |

**Что именно собирает setup.** В новом проекте он устанавливает выбранные скиллы и создаёт маршрут с подходящими точками входа. В существующем сохраняет установленные правила и ссылается на их исходные файлы. При отдельной установке `tdd` агенту достаточно самого скилла и доступных инструкций проекта. Покупать переносимость ценой обязательного полного setup для одного скилла нецелесообразно. Сегодня setup уже учитывает выбранный режим поставки и существующие документы. Изменить смысл `WORKFLOW.md` с карты на основную инструкцию маршрута — предложение. [Текущий setup](../../tools/setup.py) · Шаблон корневых инструкций (файл снимка; с 2026-11-23 корневые инструкции пишет скилл настройки)

**Пример одной поставки.** Три тикета объединены в один PR. `implement-spec` организует их выполнение. Когда готова вся поставка, ведущий агент один раз вызывает `code-review`. Оба ревьюера читают один снимок изменений. После одного прохода исправлений запускаются затронутые тесты и, если требуется, один локальный Verify. Если позже упал CI, агент исправляет причину, запускает затронутые проверки и CI на новом коммите. PR сохраняет отдельно проверенную локально версию, последующие правки и итог CI. Подключённый классификатор один раз применяет правила проекта к готовому PR. Он возвращает статус и основание. `ship` записывает их в PR и проверяет разрешение на слияние. В проекте с обязательным ручным merge последнюю кнопку нажимает владелец. В проекте с разрешённым автоматическим merge подтверждение в PR требуется в предусмотренных проектом случаях.

**Когда понадобится исполняемый координатор.** Если человек должен ответить завтра, а агент работает в открытой сессии сегодня, в PR уже можно оставить результат и ожидаемое действие. Чтобы ответ завтра сам запустил продолжение, потребуется обработчик события. Перед первым таким запуском стоит определить ключ поставки и ревизию, где сохраняется состояние, как повтор события находит прежний результат, какое изменение его инвалидирует и после скольких неудач процесс останавливается. Исполнение обязательного CI и ограничений на merge стоит поручать средствам репозитория. Текст правила сам по себе пропустить действие технически не мешает.

**Как сохранить один источник после автоматизации.** Пока этап запускает ведущий агент, переход описан в проектном workflow. Когда этот переход возьмёт на себя GitHub Actions или другой сервис, авторитетной станет исполняемая конфигурация. В документе можно дать ссылку на неё или строить схему из тех же данных. Первый повод для исполняемого перехода — конкретная работа, которую хочется запускать по событию. Координация нескольких задач и восстановление после остановки добавляют требования по мере их появления. До этого отдельный сервис, собственный YAML-формат и постоянно работающий «агент-начальник» увеличивают число мест для настройки.

**Как улучшать фабрику.** После неудачной поставки нужно определить, какое решение привело к ошибке. Ревьюер пропустил нарушенный стандарт — кандидат на правку метода ревью или на детерминированную проверку. Забыли вызвать ревью — править маршрут. Слили то, что владелец хотел увидеть, — сверить правила приёмки и фактическое разрешение на слияние. Сначала установить место сбоя по одному реальному PR, затем проверить изменение на следующем похожем случае. У Warp обратная связь может приводить к отдельному PR с изменением скилла, а у Matt для разбора предназначен `retro`. [Цикл Warp](https://github.com/warpdotdev-demos/cloud-factory-demo/blob/ab21d0c5b70e38abe1a53ff6e2934d2637415c5b/README.md) · [Matt о retro](https://www.aihero.dev/skills-retro)

## Как проверить предложение

Первый пилот — новый проект, одна настоящая задача и один PR. На нём проверить три свойства: новый исполнитель находит следующий шаг по корневой инструкции и записям задачи, отдельная установка `tdd` работает без остальной цепочки, а изменение правила приёмки требует одной правки. Для сценария с падением CI проверить счётчики вызовов: одно ревью, один завершённый Verify, новый CI и сохранённая связь с исходной версией Verify. Второй полезный пример — настроенный проект со своим классификатором и шаблоном PR. Подключение Kit должно сохранить их смысл. Сравнивать число повторных вызовов и ручных уточнений, а также токены, когда клиент их сообщает. Первое узкое сравнение проведено 21 ноября: две экспериментальные сборки и 16 прогонов моделей (эксперимент удалён 2026-11-23, остался в истории Git). Проверку переноса и возобновления в существующем проекте ещё предстоит провести.
