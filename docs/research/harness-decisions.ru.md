## Что делает человек

| Когда | Пример обращения | Что должно оказаться у владельца |
| --- | --- | --- |
| Один раз при подключении проекта | «Настрой Agent Kit для этого репозитория. Покажи, что уже нашлось и какие решения нужны от меня». | Предпросмотр изменений, источники правил и вопросы о старте, проверках, приёмке и разрешениях. Сейчас это обеспечивает CLI с явным применением. Единый пользовательский setup-скилл планируется в [№ 9](https://github.com/KirillSachkov/agent-kit/issues/9). |
| Есть идея | «Давай обсудим, как сделать экспорт заказов». | Ответ или обсуждение. Для неясного решения пригодится grilling, для согласованной большой работы — спецификация и тикеты. |
| Понятна небольшая задача | «Реализуй задачу № 42. В CSV должна появиться колонка скидки». | По предлагаемому базовому правилу это поручение начинает реализацию в проекте. У существующего проекта может быть свой обязательный способ старта. |
| Готова спецификация | «Реализуй спецификацию № 7 целиком». | Выполнение согласованных тикетов. Обычный вариант — одна общая поставка. Отдельные PR определяются заранее, если части принимаются самостоятельно. |
| Работа дошла до приёмки | Владелец просматривает подготовленный агентом PR, когда там требуется его решение, смотрит указанный сценарий и отвечает в PR. | Сохранённое решение по конкретному изменению. При разрешённом автослиянии и отсутствии требуемого просмотра агент завершает поставку самостоятельно. |

Открытый выбор — какой старт предложить новому проекту по умолчанию. Варианты: явное поручение в чате, именованный вызов скилла, событие трекера, которое само запускает сессию. Настройку репозитория и назначение каждой следующей задачи удобно рассматривать отдельно. Текущий starter допускает обычное поручение и по умолчанию использует локальную сдачу. Для PR и автослияния нужны соответствующая настройка и полномочия. [Текущие значения](../../templates/project/defaults.json)

## Согласованная работа сегментов

| Сегмент | За что отвечает и что отдаёт следующему участнику |
| --- | --- |
| Подготовка | Владелец и агент фиксируют результат, критерии и зарезервированные решения. По потребности помогают `grilling`, `research`, `prototype`, `to-spec`, `to-tickets`. Для простой задачи достаточно самого поручения. |
| Реализация | `implement` ведёт одну работу. `implement-spec` организует граф тикетов и возвращает собранную поставку. Частичные исполнители передают изменения и результаты тестов. |
| Тестирование | `testing.md` хранит доступные команды, среду, данные и принятые границы тестирования. TDD ведёт циклы разработки через публичный интерфейс. Подбор новых видов тестов и настройка анализаторов и CI — отдельная практика в разработке. |
| Ревью | Один вызов `code-review` на поставку. Standards и Spec параллельно читают один зафиксированный снимок. Требования можно передать задачей или файлом. Автор делает один проход исправлений и запускает затронутые тесты. |
| Проверка поведения | Если проект требует Verify, агент один раз проверяет исправленную версию через пользовательский вход до открытия PR. Наблюдаемый результат, побочные эффекты и границы проверки привязаны к версии. Провал обязательного сценария или недоступная среда оставляют поставку открытой. Переносимая процедура сегодня находится в [implement/VERIFICATION.md](../../skills/engineering/implement/VERIFICATION.md). Выделение в скилл — [№ 3](https://github.com/KirillSachkov/agent-kit/issues/3), создание проектных инструкций — [№ 6](https://github.com/KirillSachkov/agent-kit/issues/6). |
| Доказательства работы | Для конкретного критерия сохраняются действие, ожидание, наблюдение, версия и подходящий артефакт. Для CLI это может быть вывод или файл, для интерфейса — снимок или запись. PR использует уже полученный материал. Формат есть в [манифесте](../../templates/project/evidence-manifest.json), автоматизация сбора и передачи — [№ 4](https://github.com/KirillSachkov/agent-kit/issues/4). |
| PR и CI | `pr` оформляет отчёт по шаблону проекта. При отсутствии шаблона согласован запасной формат Matt. Видимая часть читается примерно за минуту, лимита слов нет. `ship` ведёт CI. После исправления сбоя запускаются затронутые проверки и CI на новой версии. Отчёт различает первоначальный Verify, последующие изменения и итог CI. |
| Классификация | Если практика подключена, один классификатор после технических проверок применяет правила проекта и договорённости из задачи к итоговому изменению. В PR появляются статус, основание и, когда нужно, вопрос владельцу. Полномочия на слияние задаёт проект. Сегодня это [owner-attention](../../skills/engineering/owner-attention/SKILL.md). Имя и способ подключения в следующей версии ещё обсуждаются. |
| Приёмка и доставка | Владелец принимает зарезервированное за ним решение через PR. `ship` выполняет разрешённое действие и сверяет фактическую версию. Для локального проекта конечной точкой может быть проверенный коммит и запись результата. Если задача включает выкладку, её полномочия, среду и проверку после выкладки задаёт проект. |

Эта карта задаёт смысл этапов для обеих экспериментальных сборок. Владельца переходов между ними выбираем отдельно. [Схемы A и B](../../experiments/delivery-routing/README.md) · [Действующий контракт Kit](../engineering-contract.md)

## Решения по исходным скиллам

Это целевое состояние после обсуждения. Текущие различия с закреплённым исходником можно посмотреть через `python3 tools/upstream.py diff --stat`. [Порядок сравнения](../upstream.md)

- **Полный оригинал Matt.** Сохраняем уже оригинальные `grilling`, `teach`, `to-questionnaire`, `writing-for-agents`. Согласован возврат `grill-me`, `grill-with-docs`, `research`, `handoff`, `retro`, `codebase-design`, `domain-modeling`, `wait-what`, `diagnosing-bugs`, `prototype`, `wayfinder`, `triage`, `to-tickets`, `tdd`, `wizard`. Сюда входят оригинальные GLOSSARY.md и шаблон wizard.
- **Узкие адаптации.** В `to-spec` нужна ссылка на проектные решения о тестировании. В `improve-codebase-architecture` остаётся проектный язык HTML-отчёта.
- **Связь с поставкой.** Для `implement`, `implement-spec`, `code-review` и `pr` сохраняем механику исходника и согласованные выше проектные отличия. В тексте № 10 выбор режима ещё помечен открытым. В последующем обсуждении согласован обычный режим одной общей поставки с возможностью заранее выделить самостоятельные PR. Детализация исполнения спецификации ведётся в [№ 10](https://github.com/KirillSachkov/agent-kit/issues/10).
- **Практики Kit.** `ship` отвечает за доставку. `ask` планируется как собственный навигатор по практикам и накопленным знаниям. Единый setup Kit должен заменить исходную точку входа `setup-matt-pocock-skills`. ## Что нужно от setup

Решение по № 9 — один пользовательский setup-скилл для нового, существующего и частично настроенного проекта. Он использует текущий установщик для предпросмотра и применения. При повторе с теми же решениями на той же ревизии ожидается пустой diff. Свежая сессия узнаёт правила из проекта. Название и диалог первого запуска предстоит уточнить. В пустом репозитории появляются корневой указатель, настройки и инструкция тестирования с теми сведениями, для которых есть основание. В существующем используются действующие инструкции и команды, отдельно разбираются противоречия. Наличие команды ещё не означает, что она успешно отработала. Установка одного скилла остаётся самостоятельным путём. [Текущий setup](../../tools/setup.py) · [Установка отдельного скилла](../distribution.md)

Для пилота важны три разные операции: установка скиллов, настройка прав и порядка работы, автоматический запуск сессии по внешнему событию. Первый релиз может дать понятный путь от поручения до приёмки в чате. Для автономного продолжения после ответа в PR потребуется исполнитель события с проверкой версии и защитой от повторной обработки. Выбор такого исполнителя и превращение WORKFLOW.md в основной маршрут пока обсуждаются.

## Какой вопрос остался после 16 прогонов

В A агент однажды неверно описал в PR, какая правка произошла после Verify. В B агент однажды пропустил затронутые тесты после исправления замечания и сразу прошёл Verify. Ещё в B первая попытка исправить упаковку не прошла CI, а следующая прошла. Повтор исправления CI укладывается в правила. Оба варианта получили 7/8 по операциям поставки. В опыте лежали готовый TASK.md и политика, а промпт прямо поручал прочитать AGENTS.md и довести задачу до конца. Проверка открытия сессии по событию, первой установки и ответа живого владельца лежит за пределами этого сравнения. [Исходный промпт](../../experiments/delivery-routing/run.py) · [Протокол и ограничения](../../experiments/delivery-routing/RESULTS.md)

Предлагаемый следующий тест — чистая установка в новом проекте и два обращения в свежих сессиях: обсуждение идеи и прямое поручение реализовать небольшую задачу. Наблюдения: начал ли агент писать только после поручения, нашёл ли правила без подсказки про AGENTS.md, смог ли показать ожидаемый результат и корректно дойти до предусмотренной приёмки. Для режима событий отдельная проверка — продолжение по ответу в PR после закрытия первой сессии. Эти опыты остаются предложением.
