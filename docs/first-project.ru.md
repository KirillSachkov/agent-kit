# Первый проект с Agent Kit

[English](first-project.en.md)

Для первой пробы возьми пустой локальный Git-репозиторий. Задача пробы — настроить его так, чтобы новая сессия могла объяснить путь первой задачи и точку решения владельца. Нужны Git, Python 3.11+ и рабочая копия Kit.

## Настроить проект

Из каталога Kit укажи существующую папку проекта и выбранный коммит:

```bash
project=/absolute/path/to/project
kit_ref=$(git rev-parse HEAD)
python3 tools/setup.py --project "$project" --ref "$kit_ref"
```

Посмотри предложенные настройки, список скиллов и diff. Полный набор включает все выпускаемые скиллы на этой ревизии. Практики применяются по задаче: вопрос можно закончить ответом, для большой поставки пригодятся `to-spec`, `to-tickets` и `implement-spec`. Правила проекта определяют необходимость TDD, локального Verify и решения владельца.

В существующем проекте проверь, откуда setup взял инструкции, трекер, тесты, файлы CI и правила доставки. Сверь локальную настройку с правилами команды. Например, обязательный повтор Verify после CI меняет принятый цикл: согласуй это расхождение до применения. Для проекта без внешнего CI достаточно его локальных проверок.

```bash
python3 tools/setup.py --project "$project" --ref "$kit_ref" --apply
python3 tools/skills.py check --project "$project"
python3 tools/setup.py --project "$project" --ref "$kit_ref"
```

При повторе с тем же SHA и теми же решениями diff пуст. Настройки доступны через `python3 tools/setup.py --help`. Для одного скилла используй [выбор с зависимостями](distribution.md).

## Решения существующего проекта

Передай `--decisions /path/to/decisions.json` при предпросмотре и применении. Например, для проекта с PR и своей инструкцией тестирования:

```json
{"language": "ru", "delivery": "pr", "testing_file": "docs/TESTING.md"}
```

Файл должен уже существовать по указанному пути внутри проекта. Сверь итоговый diff и разделы, где setup просит решения о доступе, старте или приёмке. Применение шаблона само по себе не даёт права на merge или публикацию.

Доступные настройки перечислены в [проектных значениях по умолчанию](../templates/project/defaults.json). Если оба корневых файла содержат самостоятельные инструкции, укажи `instruction_owner`. Согласованное исключение запиши в `resolution`. Setup сохраняет чужие файлы и сообщает о локальных изменениях в управляемых файлах до записи. Для двух клиентов укажи `--client both` при первом предпросмотре и применении.

## Что прочитает агент

- Корневые инструкции указывают условия старта, рабочую копию, способ сдачи и полномочия. [Две схемы](../templates/project/WORKFLOW.md) показывают развилки.
- Спецификация описывает ожидаемый результат задачи. `testing.md` или существующая инструкция проекта объясняет, на какой границе, какой командой, с какими данными и в какой среде его проверить. Найденная команда и успешный запуск имеют разный статус. Подбор и настройка новых типов тестов, статических анализаторов и CI отдельным скиллом — **в разработке**.
- Один PR или одна локальная сдача получает один вызов `code-review`. После параллельных Standards и Spec идут один проход правок, затронутые тесты и, если нужен, локальный Verify. Неудачный сценарий и недоступная среда оставляют обязательный критерий открытым.
- Если Verify прошёл на A, а CI потребовал правки на B, в сдаче остаются результат Verify на A, изменения после A, затронутые тесты и CI на B. Классификатор, когда включён, один раз определяет, нужно ли решение владельца. Агент сверяет результат разрешённой доставки с целевой веткой.

Открой свежую сессию в проекте и попроси: «Команда должна объяснять, почему входной файл не найден. По каким файлам ты решишь, когда начать, как проверить это поведение и где нужен я?» Первая проба завершена, когда агент может показать эти места, а повторная настройка предлагает пустой diff.
