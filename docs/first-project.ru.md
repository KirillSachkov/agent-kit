# Первый проект с Agent Kit

[English](first-project.en.md)

Для первой пробы возьми пустой локальный Git-репозиторий. Задача пробы — настроить его так, чтобы новая сессия могла объяснить путь первой задачи и точку решения владельца. Нужны Git, Python 3.11+ и рабочая копия Kit.

## Настроить проект

Из каталога Kit укажи существующую папку проекта и выбранный коммит:

```bash
project=/absolute/path/to/project
kit_ref=$(git rev-parse HEAD)
python3 tools/setup.py --project "$project" --ref "$kit_ref"
```

Посмотри предложенные настройки, список скиллов и diff проектных файлов. Изменения внутри скиллов показаны по строке на скилл, полный diff даёт `--full`. Полный набор включает все выпускаемые скиллы на этой ревизии. Практики применяются по задаче: вопрос можно закончить ответом, для большой поставки пригодятся `to-spec`, `to-tickets` и `implement-spec`. Настройки проекта определяют, нужна ли проверка поведения и решение владельца.

В проекте со своими инструкциями setup просит явно указать способ сдачи: `local`, `main`, `pr` или правило проекта словами. Сам он его не угадывает. Проверь список найденных документов и файлов CI и сверь настройку с правилами команды. Например, обязательный повтор Verify после CI меняет принятый цикл: согласуй это расхождение до применения. Для проекта без внешнего CI достаточно его локальных проверок.

```bash
python3 tools/setup.py --project "$project" --ref "$kit_ref" --apply
python3 tools/skills.py check --project "$project"
python3 tools/setup.py --project "$project" --ref "$kit_ref"
```

При повторе с тем же SHA и теми же решениями diff пуст. Затем один раз вызови в проекте `$setup-matt-pocock-skills`: он настраивает трекер, метки и доменные документы, которых ждут `to-spec`, `to-tickets` и `triage`. Если проекту нужна проверка поведения, вызови `$create-verification-skill`: он создаст проектный скилл `verify-<приложение>`. Настройки доступны через `python3 tools/setup.py --help`. Для одного скилла используй [выбор с зависимостями](distribution.md).

## Начать работу в новой сессии

В таблице приведены команды Codex. В Claude Code начни сообщение с команды через косую черту, например `/to-tickets <спека>`. В этом же сообщении можно принять спеку и сразу запросить разбивку.

| Что ты хочешь | Что сказать | Где остановится агент |
| --- | --- | --- |
| Разобраться в issue | «Почему в № 42 пропадает скидка?» | Покажет пример и объяснит причину. |
| Подготовить спеку | `$grill-me` для обсуждения, затем `$to-spec` для записи решения | Даст ссылку на сохранённую спеку. |
| Принять спеку и разбить её на тикеты | «Спеку принимаю. `$to-tickets <спека>`» | Покажет тикеты и зависимости. После твоего согласия сохранит разбивку. |
| Реализовать согласованные тикеты | `$implement-spec <спека>` | Реализует тикеты на общей ветке и проведёт одно ревью. |
| Решить одну поставленную задачу | `$implement <issue>` | Реализует, закоммитит и проведёт ревью. |

Если ты сказал только «спеку принимаю», агент назовёт следующую команду, `$to-tickets`, и остановится. После записи тикетов реализацию запускаешь отдельно. Скиллы, помеченные как вызываемые человеком, агент сам не запускает: это задано флагами скиллов и строкой в корневых инструкциях проекта.

## Решения существующего проекта

Передай `--decisions /path/to/decisions.json` при предпросмотре и применении. Например, для проекта с PR и своей инструкцией тестирования:

```json
{"language": "ru", "delivery": "pr", "testing_file": "docs/TESTING.md"}
```

Файл должен уже существовать по указанному пути внутри проекта. Сверь итоговый diff и разделы, где setup просит решения о доступе, старте или приёмке. Применение шаблона само по себе не даёт права на merge или публикацию.

Доступные настройки перечислены в [проектных значениях по умолчанию](../templates/project/defaults.json). Если оба корневых файла содержат самостоятельные инструкции, укажи `instruction_owner`. Если предпросмотр обнаружил расхождения, согласуй решение с владельцем проекта. Запиши его в `resolution` и скопируй показанный `conflict_id` в тот же JSON-объект. Когда расхождения меняются, согласуй новый предпросмотр и укажи его идентификатор. Setup сохраняет чужие файлы и сообщает о локальных изменениях в управляемых файлах до записи. Для двух клиентов укажи `--client both` при первом предпросмотре и применении.

## Что прочитает агент

- Корневые инструкции указывают условия старта, рабочую копию, способ сдачи и полномочия. [Короткий маршрут](../templates/project/WORKFLOW.md) хранит правила связи скиллов, [карта частей](parts.ru.md) показывает, какой скилл за что отвечает.
- Спецификация описывает ожидаемый результат задачи. `testing.md` или существующая инструкция проекта хранит стратегию тестирования: на какой границе и каким видом теста проверяется каждый вид изменений. Её читают `to-spec` и `tdd`. Команды запуска агент берёт из самого проекта.
- Один PR или одна локальная сдача получает один вызов `code-review`. После параллельных Standards и Spec идут один проход правок, затронутые тесты и, если нужен, один проход проектного скилла `verify-<приложение>`. Вердикт `FAIL` или `BLOCKED` оставляет сдачу открытой.
- `ship` открывает PR, добивается зелёных обязательных проверок и убеждается, что слияние действительно произошло. Сливает он только когда проект это разрешает. Доказательства проверки хранятся так, как задано в настройке `evidence`: вложениями PR (по умолчанию на GitHub), в папке репозитория, во внешнем хранилище или только текстом.
- Стандарты кода читает ревью, а не исполнитель. Файл `CODING_STANDARDS.md` при установке не создаётся: когда ревью пропустило ошибку, вызови `$retro`, и он предложит либо автоматическую проверку, либо правило в этот файл.

Открой свежую сессию в проекте и попроси: «Команда должна объяснять, почему входной файл не найден. По каким файлам ты решишь, когда начать, как проверить это поведение и где нужен я?» Первая проба завершена, когда агент может показать эти места, а повторная настройка предлагает пустой diff.
