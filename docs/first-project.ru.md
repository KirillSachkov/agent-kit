# Первый проект с Agent Kit

[English](first-project.en.md)

Для первой пробы возьми пустой локальный Git-репозиторий. Задача пробы — настроить его так, чтобы новая сессия могла объяснить путь первой задачи и точку решения владельца. Нужны Git, Python 3.11+ и рабочая копия Kit.

## Установить скиллы

Из каталога Kit укажи существующую папку проекта и выбранный коммит:

```bash
project=/absolute/path/to/project
kit_ref=$(git rev-parse HEAD)
python3 tools/setup.py --project "$project" --ref "$kit_ref"
python3 tools/setup.py --project "$project" --ref "$kit_ref" --apply
python3 tools/skills.py check --project "$project"
```

Первая команда показывает, что изменится: по строке на скилл и diff корневых инструкций, полный diff даёт `--full`. Вторая применяет. Команда ставит скиллы, блок указателей в корневые инструкции и короткий `WORKFLOW.md`. Решений о проекте она не принимает. Твои инструкции и файлы она не меняет, а при повторе с тем же SHA diff пуст. Для двух клиентов добавь `--client both`. Если и `AGENTS.md`, и `CLAUDE.md` содержат самостоятельные инструкции, укажи главный файл через `--instruction-owner`. Для одного скилла используй [выбор с зависимостями](distribution.md).

## Настроить проект

Открой сессию в проекте и вызови `$setup-agent-kit`. Скилл обследует проект и проводит короткое интервью, в каждом разделе предлагая ответ, который можно принять одним словом:

| Раздел | Что решается |
| --- | --- |
| Язык | на каком языке агент пишет для людей |
| Трекер | где живут задачи: GitHub, GitLab, локальные файлы или свой вариант |
| Метки | названия ролей готовности задач |
| Доменные документы | где лежат `GLOSSARY.md` и ADR |
| Сдача | локально, в `main`, через PR или своё правило словами; обязательные проверки и CI |
| Проверка поведения | когда нужна, кто проводит, где хранить доказательства |
| Приёмка | каждая сдача ждёт тебя, по странице условий или без проверки |
| Существующие правила | что оставить там, где правила проекта расходятся со скиллами |

Перед записью скилл показывает черновик. Результат лежит в `docs/agents/`: настройки, трекер, метки, доменные документы, стратегия тестирования. Вызови скилл снова, чтобы изменить решение: он покажет текущие и спросит только о том, что меняется, и о настройках, появившихся в новой версии Kit. Если проекту нужна проверка поведения, после настройки вызови `$create-verification-skill`.

## Начать работу в новой сессии

В таблице приведены команды Codex. В Claude Code начни сообщение с команды через косую черту, например `/to-tickets <спека>`. В этом же сообщении можно принять спеку и сразу запросить разбивку.

| Что ты хочешь | Что сказать | Где остановится агент |
| --- | --- | --- |
| Разобраться в issue | «Почему в № 42 пропадает скидка?» | Покажет пример и объяснит причину. |
| Подготовить спеку | `$grill-me` для обсуждения, затем `$to-spec` для записи решения | Даст ссылку на сохранённую спеку. |
| Принять спеку и разбить её на тикеты | «Спеку принимаю. `$to-tickets <спека>`» | Покажет тикеты и зависимости. После твоего согласия сохранит разбивку. |
| Реализовать согласованные тикеты | `$implement-spec <спека>` | Реализует тикеты на общей ветке и проведёт одно ревью. |
| Решить одну поставленную задачу | `$implement <issue>` | Реализует, закоммитит и проведёт ревью. |

Если ты сказал только «спеку принимаю», агент назовёт следующую команду, `$to-tickets`, и остановится. После записи тикетов реализацию запускаешь отдельно. Скиллы, помеченные как вызываемые человеком, агент сам не запускает: это задано флагами скиллов.

## Что прочитает агент

- Корневые инструкции указывают на настройки проекта и говорят, где можно начинать реализацию. [Короткий маршрут](../templates/project/WORKFLOW.md) хранит правила связи скиллов, [карта частей](parts.ru.md) показывает, какой скилл за что отвечает.
- Спецификация описывает ожидаемый результат задачи. `testing.md` или существующая инструкция проекта хранит стратегию тестирования: на какой границе и каким видом теста проверяется каждый вид изменений. Её читают `to-spec` и `tdd`. Команды запуска агент берёт из самого проекта.
- Один PR или одна локальная сдача получает один вызов `code-review`. После параллельных Standards и Spec идут один проход правок, затронутые тесты и, если нужен, один проход проектного скилла `verify-<приложение>`. Вердикт `FAIL` или `BLOCKED` оставляет сдачу открытой.
- `ship` открывает PR, добивается зелёных обязательных проверок и убеждается, что слияние действительно произошло. Сливает он только когда проект это разрешает. Доказательства проверки хранятся так, как записано в настройках проекта: вложениями PR (по умолчанию на GitHub), в папке репозитория, во внешнем хранилище или только текстом.
- Стандарты кода читает ревью, а не исполнитель. Файл `CODING_STANDARDS.md` при установке не создаётся: когда ревью пропустило ошибку, вызови `$retro`, и он предложит либо автоматическую проверку, либо правило в этот файл.

Открой свежую сессию в проекте и попроси: «Команда должна объяснять, почему входной файл не найден. По каким файлам ты решишь, какими тестами это покрыть, как проверить поведение и где нужен я?» Первая проба завершена, когда агент может показать эти места, а повторная установка предлагает пустой diff.
